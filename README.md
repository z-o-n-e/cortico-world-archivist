# 备份与恢复 / Backup & Restore

给 [Coopanion](https://github.com/Pal-AI-Lab) 用的 World 扩展（包名 `cortico-world-archivist`，配置段 `worlds.archivist`）：**定期备份 + 一键恢复**。

她的长期记忆散在三个地方——`workspace/`（画像、自述、日记、笔记、交接档案）、`data/*.json`（事实库、向量索引、档案、反思、画像卡）、`config.json` + `.env` + `providers/`（配置与密钥）。这个扩展把三处打成一个 zip，滚动保留若干份；要回退时从任意一份放回去。

> ⚠️ **这三处说的是「备份打些什么」，不是「恢复碰些什么」。**
> 恢复的覆盖面大得多，见下面[恢复](#恢复)一节——它会覆盖**所有扩展的数据**、**所有 World 的配置**和**全部密钥**。

**零上下文成本**：不进系统前缀（`envPromptVars()` 返回 `null`）、不注册任何工具（`tools()` 返回 `[]`）。它只在后台跑，不吃 token。

## 装

```
pnpm add cortico-world-archivist        # 或在扩展市场里装
```

装完重启 Coopanion，在「世界」页启用「归档」，再打开它的配置页。

## 备份

| 配置项 | 说明 |
| --- | --- |
| 备份间隔 | 多久一次（小时）。进程重启后会检查是否超期，超了就立刻补一次 |
| 保留份数 | 滚动保留。超过就删最老的 |
| 存放位置 | zip 放哪。留空 = **部署目录**下的 `archivist/`（在 `data/` 之外，不会被下一次备份打包进去）。**建议放到另一块硬盘或网盘同步目录** |
| 备份内容 | 五项可勾：工作区全部 / git 历史 / blobs 附件 / 扩展数据 / 配置与密钥 |
| 连带扩展包 | 把 `extensions/` 也打包。几十 MB，一般不用 |
| 额外要备份的路径 | 一行一个。给那些把数据放在子目录、或装在别处的扩展补漏 |
| 立即备份一次 | 拨到开 → 一分钟内开始，做完自动关回去 |

「上次结果」那一组里还有两个**只读**的展示项：「实际存放位置」是真正生效的绝对路径（留空时由扩展算出默认值），「备份占用」是「N 份，共多少、最大一份多大、日期范围」。用来判断旧备份有没有异常膨胀，或者直接照路径去文件管理器手工清理。

**存放位置绝不能落在 `data/` 里。** 「扩展数据」会整目录扫描 `data/`，把备份目录放在那里等于每一份新 zip 都把之前的 zip 一起打包——zip 已经压过，再压一次几乎不变小，单份体积逐次接近翻倍，几天就能吃掉整块盘，或者让 `Compress-Archive` 因为单文件过大而失败。

**但 0.3.4 起，就算你真的把它放回 `data/` 里，也不会再自我打包。** 判定按绝对路径做（`isInside()`），存放位置与它下面的 `before-restore-*` 在**备份、快照、恢复**三处一律排除：

| 环节 | 不排除会怎样 |
|---|---|
| 备份 | 每份新 zip 把旧 zip 一起打进去，体积滚雪球 |
| 快照 | `before-restore-*` 里的旧 zip 被再拷一份 |
| 恢复 | 恢复 `data/` 时把备份目录本身覆盖成旧版本，刚拿到的包当场弄坏 |

所以老配置**不需要迁移**。已用默认位置（`<data>/archivist`）的部署升级后位置保持不变，`0.3.4` 起上一节那个滚雪球问题自动消失，用户什么都不用做。只有当 `<data>/archivist` 里**一个 zip 都没有**时（装过但从没成功备份过），才会切到新的默认位置。

### 升级后建议做一次体检

如果你是从 0.3.3 或更早升上来的，之前的备份可能已经滚过雪球。建议：

1. 拨一次「**立即备份一次**」，看「上次结果」里的体积——跟上一份差不多就说明已经正常了。
2. 打开配置里的「**实际存放位置**」那一栏，把路径粘到文件管理器，看一眼里面有多少个 zip、各多大。**用不上的旧 zip 直接删掉**即可，扩展只在自己轮转时删，不会拦着你手动清理。
3. 「**备份占用**」那一栏会给出「N 份，共多少、最大一份多大、日期范围」，用来判断是否异常。

（这两栏是只读的展示项：路径由扩展算出真实生效值，占用情况在每次备份后刷新。）

「扩展数据」是**自动扫描** `data/` 目录的：装了什么扩展就备份什么，不用手动配。只跳过明确可重建的东西（运行态 JSON、缓存、`session-main.jsonl` 这类流水、任意层级的浏览器 profile，以及 `media/`、`figures/`、`emoji/` 这些几十上百 MB 的素材目录）。判定标准写在 `src/config.js` 的 `DATA_SKIP` / `DATA_SKIP_DIRS` / `DATA_SKIP_ANY_DIR` 里，附了每一条的理由。

一份真实部署（9 MB 工作区 + 13 MB 记忆数据）打包后约 **15 MB，4～5 秒**。

## 恢复

> ### ⚠️ 恢复的覆盖面
>
> 恢复**不只是把「她的记忆」放回去**。它按备份里的内容原样写回原位，所以实际覆盖的是：
>
> | 覆盖什么 | 具体是 |
> | --- | --- |
> | **所有扩展的数据** | `data/` 下**每一个**扩展存的东西：记忆库、事实库、向量索引、档案、卡片、表情包索引、词汇本……不只是本扩展或记忆类扩展 |
> | **所有 World 的配置** | `config.json` 里的**每一个 Worlds 段**（桌面宠物、QQ、语音、社交、做梦、画画……），不只是 `worlds.archivist` |
> | **全部密钥** | `.env` 与 `providers/` 下所有模型渠道的 Key 和地址 |
>
> 备份之后的**新文件不会被删除**（只覆盖、不删除），但**已有文件会被换成备份时的版本**。文件被覆盖前会先存到 `before-restore-<时间>/`，见下面第 3 步。

恢复默认**只用于灾难恢复**，所以设了两道闸：

1. **确认口令**：必须先输入 `RESTORE`（或「恢复」），否则「立即恢复」开关不动。
2. **先留存再覆盖**：恢复前把当前状态复制到 `<存放位置>/before-restore-<时间>/`，后悔了还能拿回来。

流程是固定的四步，顺序不能颠倒：

```
① 解压到临时目录      —— 不碰真实数据
② 校验 MANIFEST.md    —— 不是本扩展的包直接拒绝
③ 快照当前状态        —— before-restore-<时间>/
④ 才复制覆盖
```

第 ③ 步快照的范围与第 ④ 步覆盖的范围**一一对应**：`workspace/` 的各个子项、`data/` 的顶层数据文件**和每个会被整包覆盖的子目录**、`config.json` / `.env` / `providers/`、以及额外路径（存在快照的 `extra/` 下，按包内名字对应）。所以任何一个被恢复覆盖的位置都拿得回来。

**恢复完必须重启 Coopanion。** 记忆类扩展（如 memory-extra）把数据缓存在内存里、每 2 秒全量 flush 一次，不重启会被旧内存写回去。`workspace/*.md` 是每次现读的，会立刻生效。

所以恢复完会再等 3 秒复查一遍：如果 `data/` 里的文件在恢复后立刻被改写（内容变了，不只是时间戳），说明进程正把旧数据写回磁盘，这时结果里会直接说「这次恢复对它们无效，请完全退出 Coopanion 后重新恢复」，而不是留下一个看起来成功的假象。

恢复与备份共用「备份内容」那份勾选：备份时打包哪些，恢复时就放回哪些。

只覆盖、不删除：备份之后新写出来的文件不会被删掉。

### ⚠️ 恢复旧备份 + 扩展升级过 = 可能读出错的数据

备份是**过去某一刻的数据**，而现在跑的是**此刻的扩展代码**。中间只要有一次扩展升级，就可能出现版本错位：

| 情况 | 结果 |
|---|---|
| 新版本加了字段 | 旧数据缺字段，新版按默认值处理，通常无害 |
| 新版本改了字段名 / 结构 | **旧字段被静默忽略**——看着像恢复成功了，实际丢内容 |
| 新版本完全解析不了旧格式 | 回退成空数据，**下一次 flush 就把磁盘上的内容盖掉** |

第三种最危险，因为它不报错：`load()` 的 `catch` 会静默退回空状态，等扩展下一次落盘，你原本还能救的数据就没了。

所以两点建议：

1. **不要把很旧的备份恢复到一个已经升级过的扩展上**，除非确认过版本兼容。必要时先把该扩展降回备份时的版本，恢复完再升级。
2. **备份里记了扩展版本清单**（zip 根目录的 `EXTENSIONS.json`）。恢复时会拿它跟当前装的版本比对，结果里直接列出「哪个包从哪个版本变到了哪个版本」，不用自己猜。

### 灾难恢复的正确顺序

```
① 先装好所有扩展（和备份时尽量同版本）
② 完全退出 Coopanion
③ 再恢复备份
④ 启动
```

**先装扩展、后恢复**。反过来的话，扩展会在恢复后启动并立刻把内存里的状态 flush 回磁盘，把刚恢复的数据盖掉——虽然恢复后的 3 秒复查会当场发现并报出来，但那时候已经晚了。

另外，卸载重装 Coopanion 一般**不会**清掉 `data/` 目录，所以文件多半还在原地；这也是「装了扩展之后它自动读到了旧数据」的原因——多数扩展的 `load()` 只要文件在就会读进来，不会用空数据覆盖。真正的风险是**格式对不上**，不是文件被删除。

跨平台：Windows 的 `Compress-Archive` 会把条目名写成 `data\fact-store.json`（zip 规范要求 `/`）。Windows 自己解压没问题，但拿到 macOS/Linux 上会变成一堆名字里带反斜杠的平铺文件。所以解压后会就地修正这类条目名，`..` 一并过滤掉。

### 老配置自动迁移

配置里的源 id 改过名（早期版本叫 `memory`，现在是 `data`）。构造时会自动改名、补齐缺的源、删掉多余的键，并写回一次配置——否则面板读到 `undefined` 会把勾选框画成「没勾」，一保存就真的把那一类数据关掉了。迁移只在真的需要时才写盘。

## 日志

`<存放位置>/archivist.log`，一行一条，带 ISO 时间和级别：

```
2026-11-05T10:01:24.742Z INFO  开始备份（启动补备份）
2026-11-05T10:01:28.733Z INFO  备份完成 E:\Coopanion-Archive\archivist-2026-11-05T18-01-21.zip（15.4 MB，3960 ms）
```

和 zip 放在一起，出了问题直接把这个文件发出来就行。超过 512 KB 会截断到后一半（这不是审计日志）。

`WorldContext` 没有 `log` 字段（api 6 只给 `cfg` / `botDir` / `dataDir` / `persist` 这些），所以在扩展里写 `ctx.log?.info?.(...)` 是**空转**——这也是为什么它自己写文件，而不是指望框架的日志。

## 已知限制

- zip 打包和解压调系统能力（Windows 用 `Compress-Archive` / `Expand-Archive`，macOS/Linux 用 `zip` / `unzip`），不引第三方依赖，所以打包时源文件被并发改写可能进包失败——这也是先复制到临时目录再压缩的原因。
- 恢复 `config.json` 会连 `worlds.archivist` 这一段一起还原，包括当时的「存放位置」。如果你改过存放位置，恢复后它也会变回去。
- 快照与备份都会跳过浏览器 profile（`*‑profile`），所以这些缓存不在回滚范围内——它们本来也能重建。
- 恢复**只覆盖、不删除**：备份之后新写出来的文件会留在原地，不会因为你回退到旧备份而消失。
- 不做增量备份，每次都是全量。这样单份 zip 自包含，恢复时不用找链条。

## 开发

```
node --check src/index.js    # 语法
```

`src/` 四个文件：`index.js`（导出 World 定义）、`world.js`（生命周期、定时器、面板开关兑现）、`config.js`（默认值 + JSON Schema 表单 + 跳过名单）、`backup.js` / `restore.js`（两个执行器）。

配置表单走 `webUi().config`（纯 JSON Schema，WebUI 直接渲染），不走 `webUi().panels`——后者需要预先构建 `cortico.webUiClient` 产物。
